# DataForge

[![CI](https://github.com/Brokenheart100/DataForge/actions/workflows/ci.yml/badge.svg)](https://github.com/Brokenheart100/DataForge/actions/workflows/ci.yml)
[![Marketplace](https://img.shields.io/visual-studio-marketplace/v/dataforge.dataforge-ide?label=marketplace)](https://marketplace.visualstudio.com/items?itemName=dataforge.dataforge-ide)

Install it from the [Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=dataforge.dataforge-ide)
(extension id `dataforge.dataforge-ide`) or from the VSIX on the releases page.

A PostgreSQL-first database IDE for VS Code with a neo-brutalist workbench.
Phases 1–3 are complete and Phase 4 added a second driver: manage connections,
browse schemas/tables/views/columns, run SQL, read results, edit table rows in a
grid with transactional commit, optimistic locking and CSV export, and complete
SQL through VS Code's own language services. PostgreSQL gets the full feature
set; MySQL currently covers connections, metadata and queries. The explorer nests
`Databases → database → schemas → tables`: extra databases open read-only, and a
connection can be pointed at another database in one click.

```text
extension/           VS Code extension (Node 22+, CommonJS bundle via esbuild)
  src/domain         profiles, errors, driver ports, pending-change model
  src/application    connection/query/schema/data-editor/export services + ports
  src/infrastructure PostgreSQL + MySQL drivers, SQL builder, CSV writer, SecretStorage
  src/presentation   tree view, webview panel, message router, logging
  media              activity bar icon
webview/             Vue 3 + Pinia + Tailwind + AG Grid workbench (browser target)
shared/              dependency-free message protocol used by both sides
```

## Quick start

```bash
npm install
npm run build      # extension/dist/extension.js + extension/dist/webview
```

Then press <kbd>F5</kbd> (run configuration **Run DataForge Extension**) and open
the **DataForge** activity bar view. The workbench HTML is generated by the
extension host so the CSP nonce stays host-controlled; the webview bundle only
ever receives typed messages.

`npm run dev` starts the Vite dev server on <http://localhost:5174> with an
in-memory demo host (`DemoTransport`) so the UI can be iterated in a plain
browser. `npm run package` builds `dataforge.vsix`.

## Tests against a real PostgreSQL

Most tests are hermetic. The driver suite additionally talks to a live server
when `DATAFORGE_TEST_PG` is set:

```bash
docker run -d --rm --name dataforge-pg -p 5433:5432 \
  -e POSTGRES_PASSWORD=forge_test -e POSTGRES_DB=forge postgres:17-alpine

DATAFORGE_TEST_PG=postgres://postgres:forge_test@127.0.0.1:5433/forge \
  npm run test:unit -w extension
```

It verifies identity probing, metadata queries, result mapping, row truncation,
affected-row counts, server-side cancellation, page loading with `xmin`
versions, transactional inserts/updates/deletes, conflict rollback, read-only
views, 2500-row CSV streaming, explicit transaction sessions (uncommitted rows
stay invisible to pool queries until `COMMIT`, `ROLLBACK` discards them) and
`explain (format json)`. The MySQL adapter has its own suite gated by
`DATAFORGE_TEST_MYSQL` (metadata, row mapping, affected rows, cancellation).
Without those variables the suites are skipped.

```bash
docker run -d --rm --name dataforge-mysql -e MYSQL_ROOT_PASSWORD=forge_test -e MYSQL_DATABASE=forge -p 3307:3306 mysql:8.4
DATAFORGE_TEST_MYSQL="mysql://root:forge_test@127.0.0.1:3307/forge" npm run test:unit --workspace extension
```

## CI/CD

Two GitHub Actions workflows live in `.github/workflows`:

| Workflow | Trigger | What it does |
| --- | --- | --- |
| [ci.yml](.github/workflows/ci.yml) | push to `main`, pull requests, manual | `verify` type-checks and builds on Node 22.x and 24.x, `lint` runs oxlint + ESLint without autofix, `test` runs Vitest against PostgreSQL 17 and MySQL 8.4 service containers, `e2e` drives the built workbench in headless Chromium with Playwright, and `package` uploads `dataforge.vsix` as an artifact. |
| [release.yml](.github/workflows/release.yml) | `v*` tags, manual | Repeats the checks, verifies the tag matches `extension/package.json`'s version, packages the VSIX, creates or updates the GitHub release, and publishes to the Marketplace when the `VSCE_PAT` secret exists. |

The integration suites run automatically: the test job exports
`DATAFORGE_TEST_PG` and `DATAFORGE_TEST_MYSQL` pointing at its service
containers, so no Docker commands are needed on a runner.

To release:

```bash
npm version 0.2.0 --workspace extension --no-git-tag-version
git commit -am "Release 0.2.0"
git tag v0.2.0
git push origin main --tags
```

Set the `VSCE_PAT` secret (an Azure DevOps personal access token with the
Marketplace *Manage* scope) to let the release job publish automatically. The
publisher is `dataforge` and the extension id is `dataforge.dataforge-ide`; the
publish step uses `--skip-duplicate`, so re-running a tag whose version is
already live is safe. Without the secret the release job still publishes the
GitHub release and skips the Marketplace step.

## Design notes

- **Passwords never cross the webview boundary.** They live in
  `vscode.SecretStorage`; messages and logs are redacted and profiles are stored
  without credentials in `globalState`.
- **Every webview message is untrusted.** `MessageRouter` validates the envelope
  and each payload with Zod before a service ever sees it, then answers with a
  typed success/error envelope carrying the same id.
- **Results are bounded.** `maxRows` is clamped to 10 000 host-side and the grid
  paints 200 rows at a time, so a wide result cannot freeze the extension host.
- **Cancellation is server-side.** Aborting a query terminates its own backend
  with `pg_terminate_backend`, and the connection is destroyed instead of being
  returned to the pool.
- **Read-only profiles** are guarded by a conservative statement check; real
  protection remains the database role's privileges.
- **Writes are data, not SQL.** The webview sends row diffs; the host validates
  them against column metadata, then the driver builds parameterised statements
  in one transaction. Identifiers are double-quoted and length-checked.
- **Conflicts abort the batch.** `UPDATE`/`DELETE` carry `xmin::text = $n`; a row
  changed by another session affects zero rows, so the whole transaction rolls
  back and only the conflicting primary keys are returned.
- **Export never touches the webview.** The host picks the path with
  `showSaveDialog` and streams rows through `pg-cursor`; a failed export deletes
  its partial file.
- **Commits and exports are cancellable.** `data.cancel` aborts the request by
  id: the driver checks between statements and always rolls back, and a
  cancelled export removes the half-written CSV.
- **Consoles are tabs, not windows.** Each connection keeps several consoles with
  their own SQL, result, error and transaction; the session key is
  `consoleId ?? connectionId`, so closing a console cancels only its own
  statement and rolls back only its own transaction.
- **The editor is VS Code's.** Completion, formatting and diagnostics attach
  through language APIs: the provider reads the host's schema cache without
  triggering I/O, `Format SQL` rewrites the selection (or the whole document)
  through `WorkspaceEdit` so `Ctrl+Z` still works.
- **History is bounded and harmless.** Every execution is recorded into
  `globalState` (200 entries, consecutive duplicates merged); a failure to
  record is logged, never surfaced as a query error.
- **Transactions own one backend.** `Begin transaction` opens a dedicated
  client with `BEGIN`, later runs go through `transaction.run`, and the host
  rolls the session back when the panel closes, the extension deactivates or
  the connection drops — a leaked session never keeps a row lock alive.

## Roadmap

- Further drivers (SQLite, SQL Server): the `ConnectionKind` values exist, the adapters do not; write them against `DatabaseDriver` following [docs/drivers.md](docs/drivers.md).
- MySQL parity: data editing, CSV export and explicit transactions are PostgreSQL-only for now.
- Known gap: closing the workbench rolls back an open transaction, but pending
  cell edits in the webview are still discarded without a prompt (see
  [docs/plan.md](docs/plan.md)).
